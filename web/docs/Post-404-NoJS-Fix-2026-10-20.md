# 게시글 404 무JavaScript 빈 화면 복구 — 2026-10-20

## 작업 상태와 범위

브랜치 `feat/member-profile`, HEAD `93578013427b14dc469a264e70817806761e2644`. 시작 시 내 댓글 연동, 공백 검증, 404 RSC/안전 복귀 개선이 미커밋·미추적이었다. 그대로 보존했다. 이번에는 앱의 디자인·Provider·개인 캐시·backend/API/DB/보안 정책을 변경하지 않았다. 커밋·push·병합·배포 없음. 별도 iyum-preview worktree는 변경하지 않았다.

이번 변경은 `package.json`의 pnpm patchedDependencies, `pnpm-lock.yaml`, `patches/next@16.3.6.patch`, `patches/README.md`, `tests/member-404-race-browser.mjs` 및 이 기록/증거이다. 이전 proxy/not-found/복귀 링크 구현은 이번에 수정하지 않았다.

## 확인된 원인

현재 설치 버전은 Next16.3.6, React19.2.4다. 설치 문서 `next/dist/docs/01-app/03-api-reference/03-file-conventions/not-found.md`에 not-found는 props를 받지 않는다고 명시돼 있다. 이전 요청별 헤더 전달은 이 계약에 맞으며 빈 화면 원인이 아니었다.

제어 API에서 첫 공개 GET은 200을 반환하면서 모의 게시글을 제거하고, 다음 공개 GET은 404 POST_NOT_FOUND를 반환한다. 지연 시간으로 추측하지 않고 순서로 재현했다. 수정 전 JS=false는 HTTP404지만 `bodyText: "", links: [], heading: []`이고 JS=true만 표시됐다. before/에 이번에 다시 실행한 실패를 보존했다.

서버 `dist/server/app-render/app-render.js`의 `renderToStream` 오류 분류는 응답 상태를404로 설정한 뒤 `getErrorRSCPayload` → `ErrorApp`을 실행한다. 이 payload의 seedData가 빈 `html#__next_error__ / head / body`다. 안내가 CSS 때문에 가려진 것이 아니라 서버 HTML에 안내 노드 자체가 없고, JS hydration이 원래 Flight 트리를 복구해야 표시되는 구조였다.

Provider·공통 헤더·AppLink·비동기 headers()를 제거한 임시 최소 앱에서도 동일했다. metadata가 없는 `/plain`과 metadata만 있는 `/meta` 모두 실제404 + 빈본문이었다. 원시 문서를 minimal-repro/min-*.html로 보존했다. 최종 패치 범위에 해당하는 `/community/posts/[postId]` 최소 경로에서는 metadata 유무와 무관하게404 + header/main/h1이 서버 HTML에 나타났다. 사용자 앱에 최소 재현 경로를 추가하지 않았다.

공식 저장소에도 같은 증상과 오류 shell이 보고돼 있다. 다만 그 보고만으로 결론내리지 않고 위 로컬 실행/설치 소스를 근거로 확인했다.
- https://github.com/vercel/next.js/issues/99793
- https://github.com/vercel/next.js/issues/95613

## 수정 방식과 선택 이유

Next 버전을 추정해서 올리거나 내리지 않고 **16.3.6 고정 pnpm 패치**를 사용한다. `getErrorRSCPayload`의 not-found 복구 중 `ctx.pagePath === '/community/posts/[postId]'`인 경우만 적용한다. Next 내부 식별자는 routeModule.definition.page(`/community/posts/[postId]/page`)와 다르다. 이 차이를 임시 서버 로그로 확인한 뒤 조건을 확정했다.

기존 loader tree에서 가장 가까운 not-found 컴포넌트를 실패한 page 대신 지정하고, 기존 `getRSCPayload(..., {is404:true})` 서버 렌더 경로를 사용한다. 기존 layout과 params 구조는 유지하고 실패한 상세 page는 다시 실행하지 않는다. UI를 중복 작성하거나 React 내부 숨김 영역을 노출하지 않는다. 응답 상태·RSC 전송 코드는 수정하지 않는다. 읽기 쉬운 로직과 설치/제거 주의사항은 patches/README.md에 있다.

해당 상세 route는 현재 단일 children 경로이며 layout에서 notFound를 호출하지 않는다. parallel slots 또는 layout의 notFound 등으로 구조가 바뀌면 이 패치를 일반화해서 사용하지 말고 재검토해야 한다. Next의 일반/Turbopack 및 dev/prod, stable/experimental 배포 번들과 CJS/ESM 소스 모두 같은 작은 조건·함수를 반영했다. minified 배포본 때문에 패치 파일 diff가 크다. source map은 변경하지 않았다. 앱 전체 오류 렌더러를 영구 대체하는 일반 해결책으로 주장하지 않는다.

## HTTP 문서 / RSC / 안전 복귀

- 직접 문서·새로고침·무JS: 200→404 조회 순서, 최종 HTTP404, 보이는 제목·설명·일반 `<a href="/mypage">` 확인. 무JS 링크 클릭으로 /mypage 이동.
- 클라이언트 Flight 전송: 기존 RSC200 transport 유지. 문서404와 혼동하지 않는다. window marker를 유지하여 전체 문서 전환이 없음을 검사.
- 내 댓글27개/3페이지에서 원문 하나가 없어지면 관련3개를 제거한24개를 서버3페이지로 다시 조회. 출발 탭/인접ID1979/기준 위치 오차10px 미만을 확인. 내 게시글27→26 및 인접ID980도 확인.
- proxy가 처음부터404를 확인하는 기존 rewrite 경로도 유지. 요청별 x-iyum-post-return 덮어쓰기와 not-found의 safeListReturn 재검증을 유지. 외부·잘못된·누락 from은 기존 공개 목록으로 처리.
- 정상, 503, gateway HTML, 손상 JSON, 다른404code, timeout을 POST_NOT_FOUND로 취급하지 않음.
- 개인 목록의 local/sessionStorage 저장, DB 변경, 자동 리다이렉트/soft404 사용 없음.
