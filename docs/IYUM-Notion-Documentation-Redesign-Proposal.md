# IYUM Notion Documentation Redesign Proposal

작성일: 2026-09-13 · 상태: **검토용 제안 / 미승인 / Notion 변경 없음**

Source of Truth: [장애인 플랫폼 프로젝트](https://app.notion.com/p/39f2758cf8378086b4c5eaf9af3f89c7)와 연결된 하위 문서.

이 문서는 기존 설계를 보존하면서 개발 전 Product Validation을 정식 의사결정 과정으로 추가하기 위한 수정 제안이다. 아래의 변경 상태와 범위 분류는 실행 결과가 아니다. 인터뷰·실험·사용자 모집도 수행하지 않았다.

**검토 범위와 한계**

- 프로젝트 루트, Home, Vision, Business 10개 문서, Product 11개 문서, Frontend 상위 및 현재 연결된 16개 문서, Backend, AI·DevOps·Dev Log·Inbox와 그 하위 페이지를 조회했다. 대형 문서는 전체 장 구조를 확인한 뒤 MVP·검증·개인정보·접근성·출시·추적성 관련 절을 집중 검토했다. 모든 문장을 개별 감사했다는 의미는 아니다.
- Backend 조회는 `truncated=true`, `unknown_block_count=3436`을 반환했다. 특히 26~32장의 관리자·ADR·추적표·MVP 범위 본문이 많이 누락되어 **해당 장의 구체적인 기존 결정은 완전 검증하지 못했다.** 장 제목과 확인 가능한 본문만 근거로 삼고, 미확인 구간은 재확인 대상으로 표시했다.
- 나머지 주요 Product·Frontend 조회에서는 Backend와 같은 누락 경고가 없었다. Notion의 `unverified` 표시는 네이티브 검증 상태이며, 프로젝트 내부의 승인 여부를 대신하지 않는다. 내부 `Confirmed — FE` 등은 별개로 보존한다.
- Home의 Problem 링크는 접근/존재 확인 오류가 났다. Architecture·Database 바로가기는 삭제 표시가 있는 빈 구형 페이지를 가리켰다. AI·DevOps·Dev Log의 조회한 하위 페이지들은 빈 페이지였다.
- 본 검토는 내부 문서 정합성 분석이다. 기존 문서에 적힌 시장 통계·경쟁사 기능·법령의 최신성까지 외부 검증한 보고서는 아니다. 해당 주장들은 사용자 검증 근거나 현재 경쟁 우위로 승격하지 않는다.

## 1. Executive Summary

**추천: 기존 Architecture를 유지하고, 그 앞에 8~12주 Product Validation과 Evidence 기반 MVP 재승인 Gate를 추가한다.** 새로운 문서 체계를 병렬로 크게 만드는 대신 기존 `제품 개요`, `KPI`, `릴리즈 전략`, `향후 기능`, 기술 추적표를 연결한다.

| 구분 | 추천 내용 |
|---|---|
| 유지 | 범장애 장기 Vision, 청각장애 초기 진입, 경험과 공식 정보 연결, 2년 차 출처 기반 RAG 방향, 3년 차 확대·개인화, 접근성·보안 기본선, 기존 FE/BE 설계와 ID |
| 수정 | 1년 차 목표를 커뮤니티 구축 중심에서 핵심 문제·해결 가치 검증 중심으로 전환. 현재 광범위한 Required MVP를 재검토 대상으로 표시. 연차·AI·가입·KPI 전제의 불일치 정리 |
| 추가 | Product Validation 허브, 가설·근거·결정의 연결, 개발 진입 Gate, Release 1별 포함 결정, 실제 상호작용과 문제 해결 지표, 1년 차 WTP 탐색 |
| 보류 | 특정 Beachhead 확정, 병원·보조기기 도메인 삭제, 특정 유료 모델·가격 확정, AI 조기 구축, 장애 상세 프로필 수집 |

핵심 진단은 “검증 개념이 없다”가 아니다. [Vision](https://app.notion.com/p/3ad2758cf83780e4a3c7f9b849397de1)은 이미 1년 차를 문제와 초기 이용자 검증으로 설명하고, [향후 기능](https://app.notion.com/p/3b32758cf83781c2927be24c99a2a848)은 Evidence 기반 승격을 요구한다. 다만 그 원칙이 **최초 MVP의 개발 전 범위 결정**까지 일관되게 적용되지 않는다.

따라서 다음 경로를 정식으로 만든다.

```text
장기 Vision / 사업 가설
→ 문제·행동·Segment 검증
→ 근거와 반증 검토
→ Product Decision
→ Release별 MVP 범위
→ 기존 Requirement·Feature·IA·Flow·Screen·FE/BE
→ 실제 사용과 운영 검증
→ 다음 결정
```

## 2. 현재 구조 진단

### 2.1 보존할 강점

1. **문서 간 책임과 추적 기반이 이미 있다.** 기능 명세 13장, IA 26장, 화면 설계 21장, Backend 30장, Frontend 구현 추적표를 활용할 수 있다. 사용자 근거를 이 연결의 앞에 붙이면 된다.
2. **기능 중요도와 출시 범위를 이미 분리했다.** 릴리즈 전략 04.5·04.13은 Must/Should/Could와 Required/Optional/Deferred를 다른 축으로 다룬다. 추천·저장은 Optional이며 미출시 UI를 노출하지 않는 원칙도 있다. 새 상태 체계로 이를 덮어쓰면 안 된다.
3. **Cold Start 대응이 이미 존재한다.** 릴리즈 전략 09.4~09.5는 초기 정보성 콘텐츠, 운영 콘텐츠 표시, 가짜 사용자 후기 금지를 명시한다. 10장은 모집·운영 Capacity·Retention 관찰을 다룬다.
4. **기본 접근성과 최소 수집이 이미 설계되어 있다.** UX 19·21·26장, Frontend 접근성, Backend 00.20·21.10~21.17을 보존해야 한다.
5. **기술 확정과 미결정을 구별한다.** FE는 Confirmed, Pending, Deferred, Superseded 등을 명시한다. 사용자 가치의 미검증 상태가 기술 결정의 무효를 뜻하지 않는다.

### 2.3 근거의 해석

사용자 조사에는 공식 통계와 모집·설계 시사점이 풍부하지만, 조회한 자료에서 실제 Discovery Interview의 참여자별 관찰 기록, 대안 해결 행동, 반증 자료와 MVP 결정의 연결은 확인하지 못했다. 통계는 모집 가설을 세우는 배경 근거이며, 특정 Segment가 IYUM을 필요로 한다는 직접 근거는 아니다.

경쟁 서비스·시장 조사·해외 사례의 기능 비교도 같은 구분이 필요하다. IYUM의 계획 기능과 경쟁사의 실제 제공 기능을 동일한 표에서 우수/미지원으로 평가한 결과를 검증된 우위로 읽으면 안 된다. 기존 비교표는 보존하되 `계획 기능 / 조사일 / 출처 / 직접 관찰 여부 / 검증할 가설`을 구분한다.

## 3. 핵심 변경 제안

아래 P0/P1은 **이번 문서 변경의 우선순위**이며 기존 기능·접근성 우선순위와 별개다.

### P0-1. 개발 전 Product Validation Gate 신설

- **현재 상태:** 검증이 Vision·향후 기능·Release에 흩어져 있고 최초 출시 과정은 개발부터 시작한다.
- **문제:** 방대한 설계를 완성한 사실이 최초 MVP의 사용자 가치 근거로 대체될 수 있다.
- **제안:** 8~12주 내 문제·행동·Segment·해결 가치·공급 측 참여·재사용을 검증하고 Go/Adjust/Pivot/Stop 결정으로 범위를 재승인한다.
- **이유:** 사용자가 요구한 사용자 문제→해결 과정→필요 기능의 순서를 의사결정 규칙으로 만든다.
- **예상 효과:** 개발 전 고위험 가정을 식별하고 검증 단위로 범위를 줄일 수 있다.
- **Trade-off:** 초기 일정이 추가된다. 검증 범위를 계속 넓히지 않도록 시간·비용 상한과 의사결정일을 사전에 정한다. 12주 경과 자체를 Go로 보지 않는다.

### P0-2. 현재 MVP를 보존하면서 Release 1별로 재승인

- **현재 상태:** Required/Optional/Deferred 구분은 있으나 여러 도메인이 동시에 Required다.
- **문제:** Architecture 완전성과 첫 사용자 가치 검증 범위가 여전히 결합되어 있다.
- **제안:** 기존 기준을 `현행 승인 Baseline`으로 보존하고 `Validation 후 재검토 대상`을 표시한다. 릴리즈 전략에 Release 1 Matrix를 추가하여 기능별 포함 여부를 결정한다.
- **이유:** 기존 승인을 몰래 취소하지 않으면서 재검토를 가능하게 한다.
- **예상 효과:** 도메인을 삭제하지 않고도 첫 Closed Beta를 하나의 완결된 문제 해결 경로로 만들 수 있다.
- **Trade-off:** 전환 중 두 기준이 공존한다. 현행/제안/승인일/대체 결정 ID를 명확히 하고, 승인 전에는 제안안을 구현 계약으로 소비하지 않는다.

### P0-3. 초기 Value Proposition과 Community 성공 기준 수정

- **현재 상태:** 통합·AI·기능 비교가 전면에 있고 Community는 구축 목표로 표현된다.
- **문제:** 여러 기능을 제공해도 기존 카페·메신저·기관 문의보다 나은 이유가 입증되지 않는다.
- **제안:** “반복되는 문제에서 당사자 경험과 공식 근거를 연결하면 기존 방식보다 도움이 되는가?”를 상위 가설로 둔다. 질문 생성→경험 답변→공식 근거→다음 행동→해결 확인의 경로를 검증한다.
- **이유:** Community를 경험 생성 메커니즘으로 다루되 실제 상호 답변 가능성까지 확인해야 한다.
- **예상 효과:** 읽기 가치·질문 가치·답변 기여 가치·재사용 이유를 나눠 판단할 수 있다.
- **Trade-off:** 운영자 Concierge가 초기 만족도를 높일 수 있지만 Community 검증을 과대평가할 수 있다. 운영자·참여 보상·자발적 이용을 반드시 분리 기록한다.

### P0-4. 근거·승인·출시 상태를 구분

- **현재 상태:** FE Confirmed와 Release Scope 체계가 이미 존재한다.
- **문제:** Confirmed/Hypothesis/MVP/Future를 하나의 상태 목록으로 넣으면 서로 다른 의미가 섞인다.
- **제안:** `Evidence 상태`, `Decision 상태`, `Target Release 및 Release Scope`, `구현 상태`를 분리한다. 기존 기술 Confirmed는 유지한다.
- **이유:** 승인된 구현 방식도 가치 검증이 안 된 기능에 속할 수 있고, 높은 사용자 필요도도 이번 출시를 보장하지 않는다.
- **예상 효과:** “무엇을 알고 있는가 / 무엇을 승인했는가 / 무엇을 출시하는가”를 명확히 한다.
- **Trade-off:** 필드가 늘어난다. 원본 레지스트리와 Release Matrix에서만 관리하고 하위 문서에는 ID·링크·해당 범위만 둔다.

### P0-5. 최소 수집과 접근성을 실험·출시 양쪽의 기준으로 연결

- **현재 상태:** REQ-MEM-001은 장애·의료 정보를 가입 필수로 요구하지 않는다. Backend 21장은 최소 수집·파생 데이터 보호를 명시한다. 접근성은 이미 MVP 기본선이다.
- **문제:** 선택 프로필이나 관심 태그를 추가하면서 정보를 과잉 수집하거나, 범위 축소를 이유로 기본 접근성까지 낮출 위험이 있다.
- **제안:** 필드별 목적·선택 여부·노출·보관·삭제·분석 전송을 먼저 결정한다. Semantic HTML·키보드·포커스·대비·상태 전달·미디어 대안을 모든 출시 화면에 적용한다.
- **이유:** 문제 검증을 위해 장애 정도나 의료 이력을 기본 수집할 필요는 없다. 관심 태그도 계정과 연결되면 민감한 상황을 드러낼 수 있다.
- **예상 효과:** 초기 참여 장벽과 불필요한 데이터 부담을 줄인다.
- **Trade-off:** 개인화·분석의 세밀함이 제한된다. 필요한 경우에만 검증된 목적을 근거로 추가 수집을 검토한다.

### P1-6. Growth 앞에 Validation과 Early Product KPI 추가

- **현재 상태:** 인터뷰·성장 목표는 있으나 질문 해결률의 의미가 불명확하고 관측 계약은 미결정이다.
- **문제:** 가입·게시 수가 실제 문제 해결이나 Community 자립성을 대신할 수 있다.
- **제안:** 기존 성장 목표는 보존하고 문제 반복성·대안 행동·성공 과업·실제 해결·재사용·운영자 의존도를 먼저 본다.
- **이유:** 단계에 맞는 판단 기준이 필요하다.
- **예상 효과:** 기능 개발량·활동량과 사용자 가치를 구별할 수 있다.
- **Trade-off:** 소수 표본의 비율이 크게 흔들린다. 모든 비율에 분자/분모와 관찰 기간을 함께 표기하고 미관측을 0으로 취급하지 않는다.

### P1-7. 수익화 학습을 1년 차부터 시작

- **현재 상태:** 사업 로드맵의 WTP 검증은 4년 차이며 수익화 문서의 연차 체계도 다르다.
- **문제:** 비용 지불자·가치·전달 비용을 늦게 알게 될 수 있다.
- **제안:** 1년 차 WTP Discovery, 2년 차 작은 Paid Experiment, 3년 차 검증 모델 확대 실험, 4년 차 확장으로 정렬한다.
- **이유:** 매출 최적화와 수익화 학습은 다른 활동이다.
- **예상 효과:** 구독·광고·제휴·B2B 중 어떤 가설을 검증할지 일찍 비교한다.
- **Trade-off:** 제품 문제 탐색이 가격 질문으로 오염될 수 있다. 실제 문제·현재 지출을 먼저 확인하고 지불 질문은 후반에 둔다. 초기 Community Paywall은 기본안으로 채택하지 않는다.

## 4. Product Validation Documentation Architecture

### 4.1 최소 구조

현재 `03. Product`의 평면적인 상위 목록을 보존하고 `제품 개요` 다음에 **Product Validation 허브 하나**를 추가한다. 허브 아래에는 레지스트리 두 개만 두고 인터뷰·실험 문서는 그 안의 템플릿으로 관리한다.

```text
03. Product
├─ 제품 개요 — Product Strategy·가치 가설·Scope 개념
├─ Product Validation [ADD]
│  ├─ 허브 본문: 원칙·8~12주 운영·Gate·MVP 반영 규칙
│  ├─ 가설 레지스트리 [ADD, DB]
│  └─ 연구·실험 기록 [ADD, DB; 원자료 권한 제한]
├─ 사용자 시나리오
├─ 요구사항 (What)
├─ 기능 명세 (How)
├─ IA / 사용자 플로우 / UX / 화면 설계
├─ 릴리즈 전략 — Release 1 Matrix·출시 Gate
├─ 향후 기능 — 보류/후속 후보와 재검토 조건
└─ UI · 프로토타입 — 제작물·설계 검증 범위

02. Business
├─ 사용자 조사 — 기존 Desk Research 원본 유지
├─ KPI — 모든 Metric의 정의·분모·측정 규칙 원본
├─ 수익화 — Revenue Model 가설의 사업 맥락
└─ 사업 로드맵 — 연차 목표 원본

08. Dev Log
└─ 의사결정 — Product Decision 기록의 원본으로 재사용
```

**신규 관리 컨테이너는 허브 1개+DB 2개를 권장한다.** 각 연구 기록은 DB 항목이며 별도 상위 문서를 증식시키지 않는다. 현재 빈 [의사결정](https://app.notion.com/p/3ad2758cf83781799be2fc8904408df0)을 활용하므로 별도 Validation Decision Log DB는 만들 필요가 없다. 허브에는 결정 원본 링크만 표시한다.

### 4.2 책임과 Source of Truth

| 문서/구조 | 목적·책임 범위 | 이곳이 원본인 내용 | 다른 문서와의 관계 |
|---|---|---|---|
| 제품 개요의 Strategy 절 | 누구의 어떤 문제를 어떤 가치 가설로 검증하는지 설명 | 현재 목표 문제·Segment 결정의 요약, 장기/초기 범위 개념 | 승인 근거는 결정 로그, 실제 출시 포함은 릴리즈 전략 참조 |
| Product Validation 허브 | 정식 Product Decision Process 운영 | 단계·Evidence 규칙·Gate·역할·변경 반영 절차 | KPI 정의를 링크하고 Release·Requirement 승격 경로를 연결 |
| 가설 레지스트리 | Problem·Behavior·Gap·Community·Trust·Retention·Segment·WTP 가설 관리 | 가설 문장·반증 조건·상태·연결 근거 | 하나의 가설에 여러 연구 기록과 결정을 연결 |
| 연구·실험 기록 | 인터뷰, 관찰, Concierge, Prototype, WTP 실험의 계획·결과 | 조사 방법·대상·실제 관찰·반증·운영자 개입 | 개인정보 원자료는 제한 영역, 일반 문서에는 비식별 요약만 |
| 의사결정 | Go/Adjust/Pivot/Stop 및 Scope 결정 | 판단·근거 ID·미확인 사항·책임자·일자·재검토 조건 | 허브·Requirement·Release에 링크. 기술 ADR와 역할 구별 |
| KPI | 측정 의미와 해석 일관성 | 지표명·정의·기간·분모·수집·제외 기준 | 실험별 목표값은 실험 시작 전에 연구 기록에서 고정 |
| 릴리즈 전략 | 실제 Shipping Scope와 단계 전환 | Release ID·Feature 포함 여부·출시 승인·운영 조건 | 제품 개요·FE/BE에는 복제 대신 해당 Release 기준 참조 |
| 향후 기능 | 아직 출시하지 않는 기능 후보 보존 | 재검토 조건·의존성·보류 이유 | 검증이 필요하면 가설 레지스트리 연결, 상세 명세는 원문 유지 |

`Problem Mapping`, `Opportunity Mapping`, `Validation 추적표`는 별도 원본 문서가 아니라 가설·연구 기록을 묶은 **뷰 또는 요약 절**로 제공한다. `Interview Plan/Guide/Participant Criteria`, `Concierge/Prototype/Usability/WTP Test`도 연구 기록의 유형별 템플릿으로 통합한다.

### 4.3 가설과 연구 기록의 최소 필드

**가설:** ID, 유형, Segment/상황, 검증할 문장, 현재 대안, 기대 변화, 반증 조건, Risk, 연결 연구 ID, Evidence 상태, 결정 ID, 다음 검토일.

**연구·실험:** ID, 가설 ID, 방법, 모집 경로·기준, 참여자 코드, 동의 범위, 기간, 비교 조건, 사전 성공/중단 기준, 관찰, 발언, 해석, 반증, 한계, 운영자/보상 개입, 결정 링크.

발언·관찰·작성자의 해석을 별도 구획으로 기록한다. 동일 참여자가 인터뷰와 실험에 참여하면 연결하되 독립 표본 두 명으로 세지 않는다. 참가자 연락처를 가설 DB나 기술 문서에 넣지 않는다.

### 4.4 Evidence Strength와 결정 상태

| 수준 | 의미 | 허용되는 해석 |
|---|---|---|
| E0 | 팀 가정·기존 설계·Desk Research에서 도출 | 탐색할 가치가 있는 가설 |
| E1 | 당사자의 구체적 최근 사례·현재 해결 행동 확인 | 문제가 있을 가능성을 직접 뒷받침 |
| E2 | 서로 다른 참여자·모집 경로에서 문제와 대안의 한계 반복 확인 | 좁은 Segment/문제의 유력 후보 |
| E3 | 비교 과업·Concierge에서 행동상 가치 및 한계 관찰 | 제한된 조건에서 해결 접근법을 지지 |
| E4 | 실제 맥락에서 재사용·자발적 상호작용 반복 관찰 | 관찰한 Segment에서 초기 제품 가치 근거 강화 |

이는 통계적 확률 점수나 보편적인 성공 기준이 아니다. 근거의 직접성·독립성·반증·관찰 기간을 함께 적는다. E4도 PMF 확정과 같지 않다.

- **Evidence 상태:** Untested / Supported / Mixed / Refuted. 불확실하면 Mixed 또는 Untested를 유지한다.
- **결정 상태:** Proposed / Approved / Superseded. 기존 Confirmed — Product/FE/Backend는 승인 주체를 나타내는 기존 라벨로 유지한다.
- **출시 축:** Target Release + Required/Optional/Deferred. Conditional은 포함 전 해결할 조건을 설명하는 판정이며 최종 Ship 결과를 대신하지 않는다.
- **구현 축:** 문서화 / 설계 / 구현 / 검증 / 배포 등 기존 추적 규칙 유지.

### 4.5 MVP 반영 규칙

```text
Hypothesis ID
→ Evidence / Experiment ID
→ Product Decision ID
→ Requirement ID
→ Feature ID
→ Release ID + Shipping Decision
→ Flow / Screen / API / Test
```

기존 ID를 재발급하지 않는다. 근거가 없는 기존 Requirement는 `기존 승인, 사용자 가치 근거 미연결`로 표시하고 재검토한다. 보안·접근성·데이터 무결성·운영 보호 요구는 사용자 선호 인터뷰를 통과해야만 유지되는 항목이 아니며 `Foundation/Guardrail` 근거 유형을 사용한다.

UI 문서: 화면 설계 → Low-Fi → 디자인 검토 → High-Fi → Prototype

기존 릴리즈 전략 05.21은 첫 출시에서 Alpha를 내부 검증과 통합할 수 있는 간소화 흐름도 제시한다. 이를 삭제할 필요는 없다.

```text
제안
기존 문서 Baseline·가설 추출
→ 8~12주 Product Validation
→ Problem / Segment Decision
→ MVP Candidate 및 Release 1 Re-scope
→ 선택한 경로의 Prototype / User Test
→ Development 진입 승인
→ MVP 개발 + 초기 콘텐츠·운영 준비
→ Internal Validation (필요 시 Alpha)
→ Closed Beta, 초기 참여군 30~50명 목표
→ Community Interaction·가치·운영 재검증
→ Open Beta
→ Public / Official Release
→ Stabilization / 다음 가설 검증
```

탐색용 저비용 Prototype은 Validation 중에도 사용할 수 있다. 검증 이후의 Prototype은 승인 후보 경로를 상세화하고 사용성을 확인하는 단계다. 두 제작물이 서로 다른 질문에 답하도록 하여 같은 화면을 두 번 완성하지 않는다.

### 7.2 8~12주 운영안

수치와 기간은 **실행 계획 초안**이다. 기존 실적이나 승인된 통과 기준이 아니다. 10주를 기본으로, 모집·접근성 지원·자연스러운 재사용 관찰에 따라 8~12주 안에서 조정한다.

| 기간 | 주요 작업 | 산출물·결정 |
|---|---|---|
| 1주 | 기존 문서 가설 추출, 모집 경로·동의·접근 가능한 조사 방식 준비 | 상위 위험 가설, 모집표, 실험 예산·종료일 |
| 2~4주 | Discovery Interview·최근 사례 복원·현재 해결 행동 확인 | 문제 Cluster, 대안의 장단점, 반증, 유력 Segment 2~3개 |
| 4~5주 | Problem/Opportunity Mapping, 응답 공급자 확보 가능성 비교 | 집중 검증할 문제 1~2개. 최초 연령/기기 가설을 수정할 수 있음 |
| 5~8주 | Concierge·정보/경험 연결 비교 실험, 저비용 Prototype 과업 | 실제 도움·다음 행동·출처 이해·질문/답변 행동·운영 시간 |
| 7~10주 | 후속 관찰, 상황 재발 시 재사용, WTP 탐색, 반증 모집 | 일회성 만족과 재사용 구별, 지불자·가치·비용 가설 |
| 10주 | Gate Review·Release 1 초안 | Go/Adjust/Pivot/Stop, 범위·조건·미해결 위험 |
| 11~12주 필요 시 | 명확한 부족 근거에 한정한 추가 실험 | 종료일·추가 질문을 제한. 무기한 인터뷰나 자동 Go 금지 |

Discovery는 처음에 **고유 참여자 24~36명 수준을 계획 후보**로 삼을 수 있다. 2~3개의 문제/상황 군을 비교하고 이후 유력 후보와 반증 사례를 보강한다. 기존 인터뷰 50명 이상 목표는 1년 차 누적 목표로 보존하며, 같은 사람의 재인터뷰를 새 참여자로 세지 않는다. 표본 수만 충족해도 검증 성공으로 판정하지 않는다.

### 7.3 Segment와 모집 원칙

- 직장인/구직자는 상황 축, 20~40대는 연령 축, 보청기/인공와우는 기기 경험 축, 수어/구어는 의사소통 축이다. 이들을 서로 배타적인 7개 시장으로 다루지 않는다.
- 우선 최근 실제 문제와 해결 행동으로 모집하고, 필요한 최소 배경 정보로 차이를 비교한다. 모든 교차조합을 채우려 하지 않는다.
- 동일 카페·지인·기관만으로 모집하지 않고 가능하면 서로 다른 경로를 사용한다. 기존 방법에 만족하는 사람, 질문을 올리지 않는 사람, 답변만 하는 사람도 포함한다.
- 채팅·문자 인터뷰, 자막, 필요 시 수어 통역 등 참여 방식의 선택권과 지원 시간을 계획한다. 지원 방식에 따른 발언·관찰의 한계도 기록한다.
- 연령·기기·의사소통 방식 중 어떤 것이 실제 문제 밀도를 설명하는지 확인한 후 Beachhead를 결정한다. 범장애 방향이나 청각장애 진입 전략을 이번 단계에서 바꾸지 않는다.

### 7.4 인터뷰·실험 질문

인터뷰는 최근 구체적 사건으로 시작한다: 언제 어떤 문제가 있었는지, 어디서 찾았는지, 누구에게 물었는지, 어디에서 막혔는지, 결국 무엇을 했는지, 시간·비용·포기한 일이 무엇인지. “이 플랫폼이 있으면 쓰겠는가?”는 직접 행동 근거를 대신하지 못한다.

Concierge는 선택한 실제 문제에 대해 운영자가 당사자 경험과 공식 출처를 연결해 제공한다. 서비스가 자동 처리했다고 가장하지 않는다. 기존 방법, 공식 정보만 제공한 경우, 경험과 공식 정보를 연결한 경우를 유사 과업에서 비교한다. 작은 표본에서 엄격한 인과효과를 주장하지 않고, 순서 효과·과업 난이도·운영자 도움을 기록한다.

Trust Test는 자료 유형을 구분하는지, 적용 대상·날짜·출처를 이해하는지, 경험담을 공식 자격 판정으로 오해하지 않는지 확인한다. 질문 의향과 별개로 실제 질문 제출·타인 질문에 답변·후속 방문을 관찰한다.

### 7.5 Gate 초안

| Gate | 확인할 근거 | 판정 |
|---|---|---|
| Problem/Segment | 독립 참여자의 구체적 사례 반복, 현재 대안의 미해결 지점, 모집·답변 공급 가능성, 반증 사례 | 특정 Segment/문제의 다음 실험 승인 또는 재탐색 |
| Solution Value | 실제 과업과 다음 행동에 도움, 공식 정보/경험 이해, 운영자 투입 대비 가치, 사용 의향 이상의 행동 | 해결 접근법 유지/조정 |
| Development | 위 근거와 승인된 최소 Scope, Prototype 과업 완결, 기본 접근성·개인정보·운영·측정 계획 | R1 개발 승인 또는 추가 실험 |
| Closed→Open Beta | 실제 질문·답변·해결·재사용, 운영자 의존, 답변 집중도, 미응답·신고 Queue 처리 가능 | 확대·유지·축소 |

실험 시작 전 정할 수치의 **예시**: 한 유력 문제에 서로 다른 모집 경로의 고유 참여자 5명 이상에서 최근 사례가 반복되는지, 대표 사용자 8명 중 6명 이상이 핵심 Prototype 과업을 중대한 도움 없이 수행하는지 등. 이 수치는 보편적인 검증 기준이 아니라 조사 설계 출발점이며, 과업·대상·운영 여건에 맞춰 사전 확정한다. 작은 표본 결과는 `6/8`처럼 표시한다.

- **Go:** 해당 단계의 핵심 가설을 지지하고 안전·운영 조건이 준비됨. 다음 단계의 제한된 투자 승인이다.
- **Adjust:** 문제 근거는 있으나 표현·접근·답변 방식·UX·Scope를 수정하고 재검증해야 함.
- **Pivot:** 현재 Segment/문제/해결 방식에 반증이 우세함. 청각장애 내부의 대안을 우선 검토하고 새로운 방향은 별도 결정한다.
- **Stop:** 사전 정한 시간·비용 안에서 가치 근거를 얻지 못하거나 운영 가능한 해결이 없음. 해당 실험/출시 투자를 중단하는 결정이며 장기 Vision 폐기를 자동 의미하지 않는다.

### 7.6 Cold Start의 구체적인 출시 조건

30~50명은 첫 참여군의 계획 범위이며 성공 기준이나 자동 출시 조건이 아니다. 실제 활동자·질문자·경험 답변자 수를 따로 본다.

1. 선택한 문제의 대표 질문에서 첫 방문자가 읽을 수 있는 유용한 콘텐츠와 공식 근거를 준비한다. 전체 도메인을 채우는 대신 R1 문제 범위의 빈 공간을 줄인다.
2. 실제 경험 제공자는 동의한 당사자로 확보하고, 편집·요약 여부와 운영 콘텐츠를 표시한다. 허구의 후기·가짜 상호작용은 기존 금지 원칙을 유지한다.
3. 초기 응답 담당, 안내할 응답 기대시간, 미응답 점검, 정보 오류 수정·신고 처리를 정한다.
4. 답변 유무뿐 아니라 도움이 된 답변·문제 해결·사용자 간 답변 비중·특정 답변자 집중도를 관찰한다.
5. 운영자 Concierge만으로 가치가 확인되면 Solution Value는 일부 지지할 수 있지만 Community Hypothesis는 아직 미검증으로 남긴다.
6. 운영자 개입을 단계적으로 줄여도 필요한 답변과 재사용이 유지되는지 확인한 뒤 공개 범위를 넓힌다. 모든 개별 게시물의 미응답을 출시 금지로 해석하지 않는다.

## 8. MVP Scope 재분류안

### 8.1 네 범위의 관계

- **Product Architecture Scope:** 현재 상세 설계를 포함한 장기 기능 구조. 원문·ID 보존.
- **MVP Candidate Scope:** 1년 차 검증 가치가 있는 후보. 구현 약속 아님.
- **Release 1 Scope:** 첫 Closed Beta에서 실제 Shipping을 승인한 최소 완결 범위.
- **Future Scope:** R1/1년 차 이후 검토할 후보. 재검토 조건을 보존.

`R1 ⊆ 승인된 1년 차 MVP ⊆ Architecture`로 관리한다. Conditional은 시간 단계가 아니라 **특정 Evidence·데이터·운영 조건이 충족되어야 한다는 조건**이다. 따라서 R1/MVP/Conditional/Post-MVP/Future를 단일 Select에서 섞기보다 Target Stage와 조건을 나눈다.

### 8.2 Domain별 검토 방향

아래는 **승인 전 분류 제안**이다. 현재 Required를 이 표만으로 변경하지 않는다.

| Domain | R1 후보 | Conditional / 이후 후보 | 확정에 필요한 근거 |
|---|---|---|---|
| 홈 | 검증된 문제 경로로 안내하는 최소 진입 | 다도메인 포털·개인화 홈 | 첫 방문자가 서비스 목적과 다음 행동을 이해함 |
| 회원·인증 | 참여에 필요한 현재 인증·계정·탈퇴·복구 | 선택 프로필·추가 로그인 수단 | 실제 가입 장벽과 계정 필요성. 소셜 로그인 자동 도입 금지 |
| 커뮤니티 | 질문·경험 열람/작성·수정/삭제·답변·해결 상태·운영 | 추천·저장·고급 평판·실시간 채팅 | 질문자와 답변자의 실제 행동, 상태 모델 적합성 |
| 검색 | 선택된 콘텐츠를 다시 찾는 최소 검색/탐색 | 네 도메인 통합·고급 필터 | 대표 과업에서 필요한 검색 범위. 기존 SCH 계약 변경은 명시 승인 |
| 복지·지원정보 | 문제에 필요한 공식 출처·설명·경험·신청 경로 연결 | 전체 정책 카탈로그·고급 추천·자동 수집 | 정보 결합 가치, 업데이트 가능성 |
| 병원·청각센터 | 해당 문제가 선택될 때 최소 사례/기관 정보 | 독립 목록·필터·후기 체계는 Conditional | 기관 선택 문제가 유력한지, 데이터·후기·운영 준비 |
| 보조기기 | 해당 문제가 선택될 때 최소 자료/경험 연결 | 독립 제품 DB·후기·비교는 Conditional | 기기 관련 문제 밀도와 구조화된 데이터 필요성 |
| 알림 | 실제 답변·처리 결과를 알 수 있는 시각적 경로 | 다양한 정책 알림·Push·Digest | 답변 확인과 재사용에 필요한 최소 수단 |
| 마이페이지 | 내 질문·답변과 최소 계정 관리 | 활동 대시보드·고급 개인화 | 자기 활동 복귀에 필요한 정보 |
| 신고·문의 | 위해/오류 신고·도움 요청·결과 확인 | 복잡한 운영 Thread·자동 분류 | Beta 운영에 필요한 보호와 처리 능력 |
| 관리자 | 포함 콘텐츠/사용자/신고·출처 수정의 최소 운영 기능 | 모든 장기 Domain의 관리 화면 | 현재 운영자가 실제 처리해야 하는 업무 |
| AI | **R1 기본안에서는 제외를 권고**하되 기존 명세 보존 | 2년 차 출처 기반 RAG, 이후 개인화 | 비AI 대비 가치·데이터 품질·권한·비용·오류 대응 검증 |
| 접근성·보안 | 모든 실제 출시 경로의 기본선 | 고급 개인 설정·미출시 미디어 기능 | 선호 실험 결과와 무관하게 유지할 품질 조건 |

공식 정보 연결이 중요하다고 해서 복지/기관/기기 DB 세 개가 전부 필요한 것은 아니다. 초기에는 선택한 문제에 대한 출처가 있는 설명과 경험 콘텐츠로 실험할 수 있다. 반대로 독립 데이터 구조가 반복 과업을 해결하는 데 필요하다는 근거가 나오면 해당 도메인을 R1에 포함한다.

### 8.3 기존 계약을 보호하는 Release Matrix

최소 열: Release ID, Requirement/Feature ID, 해결 과업, Decision ID, Required/Optional/Deferred, 포함 조건, Ship/Not Ship, 의존 기능, 접근성/운영 준비, 영향 문서.

기능을 제외할 때는 UI만 숨기는 것으로 끝내지 않는다. Route·API 권한·메뉴·검색 인덱스·알림·관리자·계측·테스트까지 검토한다. 공유 기술 구조는 유지할 수 있지만 외부에서 사용 가능한 미승인 경로를 남기지 않는다.

### 8.4 관심·상황 선택과 기존 분류 체계

현재 UI는 `Post Type + Primary Topic`이며 게시글 Tag는 Phase 2+ 후보다. 이를 유지하면서 다음을 분리한다.

- **게시글의 주제:** 지금의 Primary Topic. 어떤 내용인지 분류한다.
- **사용자의 관심/상황 선택:** 개인이 보고 싶은 정보나 현재 관심을 선택하는 별도 Preference 가설. 진단이나 장애 정도를 뜻하지 않는다.
- **연구용 Segment 메모:** 조사 목적의 최소 정보. 일반 프로필이나 공개 데이터로 자동 전환하지 않는다.

관심 선택을 저장하지 않아도 탐색이 가능한지 먼저 검증한다. 저장이 필요하면 선택·수정·삭제·기본 비공개·비개인화 경로를 정의하고, 보청기/인공와우 선택을 건강 상태로 자동 추론하지 않는다. 자발적 선택이라는 이유만으로 개인정보 고려가 사라지지 않는다. 기존 Backend 21장의 최소 수집·Derived Data 원칙과 정합적이다.

## 9. KPI Framework

**Validation → Early Product → Growth**를 주 단계로 두고 **Revenue Learning은 1년 차부터 병행**한다. Revenue Learning을 Growth가 끝난 후의 순차 단계로 배치하면 조기 학습 목적과 모순된다.

### 9.1 단계별 지표

| 단계 | 지표 | 정의/관찰 | 의사결정에 쓰는 방식 |
|---|---|---|---|
| Validation | 고유 Discovery 참여자·모집 경로 | 실제 조사한 고유 인원, 상황/경로별 분포 | 조사 Coverage. 인원 자체는 성공 조건 아님 |
| Validation | 반복 Problem Cluster | 독립 참여자의 구체적 사례와 반증을 묶은 문제 | 문제 후보 비교. 같은 인터뷰 반복 언급을 중복 집계하지 않음 |
| Validation | Problem Frequency / Severity | 정한 회상 기간 내 실제 발생 횟수·시간·포기·업무/생활 영향 | 자주 발생하는 문제와 드물지만 중요한 문제를 구별 |
| Validation | Existing Solution Satisfaction | 현재 대안·최근 결과·불만·전환 비용 | 만족도 숫자만으로 Gap을 가정하지 않음 |
| Validation | Answer Seeking / Contribution | 실제 검색·문의·질문 제출·타인 답변 | 질문·공유 의향과 행동 분리 |
| Validation | Task Success / Value | 도움 없이 정한 과업 달성/유효 시도, 기존 방법 대비 도움·다음 행동 | 사용성과 제품 가치를 별도로 판정 |
| Validation | Trust 이해 | 공식/경험/전문가 정보·기준일·적용 한계를 이해한 관찰 | 잘못된 신뢰 증가를 성공으로 계산하지 않음 |
| Validation | Repeat-use Trigger / Segment Evidence | 같은 상황 재발·새 관련 사건·후속 과업에서 다시 선택한 이유 | 재사용 기회가 없었던 사람은 별도 분류 |
| Early Product | 활성 Beta 참여자 | 모집자 중 정한 기간에 핵심 행동을 한 고유 사용자 | 30~50명 등록과 실제 참여 구별 |
| Early Product | 질문·답변 생성 | 고유 작성자·질문 수·답변 수, 운영/보상 여부 구분 | 일부 이용자만 활동을 만드는지 확인 |
| Early Product | 사용자 간 답변 비중 | 비운영자·비작성자 답변 수 / 유효 전체 답변 수 | 답변 공급의 운영자 의존도 파악. 보상 답변도 별도 표시 |
| Early Product | 응답률 | 관찰 기한 안에 유효 답변 1개 이상을 얻은 질문 / 관찰 가능한 질문 | 기존 KPI의 답변 유무 지표를 정확히 명명 |
| Early Product | 작성자 확인 해결률 | 정한 기간 안에 작성자가 해결 확인한 질문 / 관찰 가능한 질문 | ANSWERED와 RESOLVED 구별. 미확인과 미해결 분리 |

| Early Product | 운영 부하·답변 집중도 | 질문당 운영 시간, 미응답/신고 Queue, 상위 답변자 비중 | 인원 확장 가능성과 Community 지속성 판단 |

| Revenue Learning | 현재 지출·구매 행동·반복 지불·전달 비용 | 의향, 후속 행동, 실제 결제, 재구매를 다른 수준으로 기록 | 모델 선택과 실험 범위 결정 |

### 9.2 기존 목표 보존

Home·Vision의 인터뷰 50명+, 가입 1,000명+, MAU 300+, 게시글/답글 3,000+, 월 재방문율 25%+, 반복 핵심 질문 100개 목표를 삭제하지 않는다.

- 인터뷰는 **연간 연구 Coverage 목표**로 두고 고유 인원·세션 수를 분리한다.
- 가입·MAU·게시 수·월 재방문 목표는 **기존 연간 Growth 목표 / Validation 후 현실성 재검토**로 표시한다.
- 반복 질문 100개는 원문 질문량과 중복 제거한 Problem Cluster를 구분한다. 100개를 채우려고 중복·저품질 콘텐츠를 만들지 않는다.
- 자발적 질문·답변 발생 목표는 사용자 간 기여·운영자 의존·기여자 집중도로 구체화한다.
- 기존 목표 미달이 곧 사용자 가치 부재를 뜻하지 않고, 목표 달성이 곧 PMF를 뜻하지 않는다.

### 9.3 측정 계약

모든 지표에는 Owner, 분자/분모, 기간·시간대, Cohort, 제외 규칙, 데이터 원본, 수집 목적, 보존 기준, 부족 데이터 표시를 둔다. 연구 중에는 비식별 수기 기록도 허용한다.

Beta 계측 후보는 질문 생성, 유효 답변 생성, 작성자 해결 확인, 공식 출처 연결 선택, 핵심 과업 피드백, 최소한의 재방문 확인이다. 이벤트명은 구현 때 확정하며 현재 존재하는 API나 이벤트처럼 작성하지 않는다. 질문 본문·검색어·관심 태그·의료 서술을 분석 도구에 통째로 보내지 않는다. 소규모 Cohort가 개인을 드러내지 않도록 집계 공개 범위도 제한한다.

[FE Observability](https://app.notion.com/p/3c42758cf837812fa523c1e71949a500)의 기술 오류 수집을 제품 행동 추적으로 확대 해석하지 않는다. KPI의 목적이 승인된 이후 필요한 최소 수집 계약을 별도로 정한다.

검토 주기는 Validation 동안 주간, Gate 시점에는 결정 회의, Beta 동안 운영 점검+정기 학습 리뷰, Growth는 기존 월간/분기 리뷰를 유지한다.

## 11. Document Dependency Impact

### 11.1 결정 흐름과 문서 권위는 구별한다

사용자가 제시한 Vision→Business→Product→Validation→Scenario→Requirement→Feature→IA→Flow→UX→Screen→FE/BE→Release→Operation은 **학습과 전달 흐름**이다. 모든 충돌에서 뒤 문서가 앞 문서를 무조건 따르는 단일 권위 순서로 사용하지 않는다.

- Vision: 장기 목적과 유지할 방향.
- Business Roadmap: 연차별 사업 목표.
- Validation: 관찰된 근거와 불확실성.
- Approved Product Decision/Requirement: 승인된 제품 행동.
- Release Strategy: 특정 Release 포함과 공개 범위.
- UX/접근성·개인정보/운영: 출시되는 기능의 기본 제약. 다른 문서보다 아래라는 이유로 약화되지 않음.
- Backend: API·서버 검증·인증/권한·DB/업무 규칙의 기술 권위.
- Frontend: Route·상태·UI 표현·클라이언트 접근성·테스트의 기술 권위.

Validation의 결과가 곧바로 기존 계약을 변경하지 않는다. 반증→Product Decision→영향 분석→승인된 원본 변경의 단계를 거친다.

| 데이터 재사용 | 운영/법률→사용 목적→Backend 저장·검색/Vector→FE 노출 | 연구, 공개, 검색/RAG, 학습, B2B 활용을 하나의 포괄적 목적처럼 취급하지 않음. 삭제/철회 반영 검토 |
| 접근성 | UX 19·21·26→각 Screen→FE 13/16→Release 06/12 | 기본선과 실제 콘텐츠에 필요한 대안 충족, 키보드·포커스·스크린리더·Zoom/Reflow 수동 검증 연결 |
| 측정 | KPI→실험 기준→Product Analytics 결정→FE/BE 수집→운영 | 정의·분모·기간이 일치하고 기술 오류 로그와 행동 계측이 분리됨 |
| 출시 확대 | Seed/모집→실제 상호작용→운영 Queue→Gate | 가입 수만으로 확대하지 않고 자발적 공급·문제 해결·운영 용량 확인 |

### 11.3 이번 변경으로 추가하지 않을 기술 작업

Validation을 관리하기 위한 별도 제품 Backend, 범용 실험 플랫폼, Feature Flag 플랫폼, 새로운 Vector DB나 분석 스택은 이번 제안의 필수 요소가 아니다. 초기 검증은 제한된 연구 도구와 수기 기록으로도 가능하다. FE의 현행 도구 선정 및 Backend의 단순한 구조 원칙을 유지한다.

접근성도 추가 장애 유형 지원을 이유로 모든 기능을 지금 개발하라는 의미는 아니다. 실제 영상이 있으면 자막·대안을 갖추고, 영상 기능이 없으면 자막 생성 시스템을 먼저 만들 필요는 없다. 다만 Semantic HTML·키보드·포커스·대비·스크린리더 기본 품질을 시각장애 확대 시점까지 미루지 않는다.

## 12. Recommended Change Order

실제 수정은 사용자 승인 후 별도 작업으로 수행한다. 한번에 모든 문서를 재작성하지 않고 **승인 단위별 일관된 변경 묶음**으로 반영한다.

1. **현행 Baseline·조회 한계 확정.** 현재 문서/ID/승인 결정 보존, 특히 Backend 26~32장 누락 원문을 다시 확보·확인한다. 구형 링크와 중복 절을 기록한다.
2. **문서 책임·상태 축·Validation Architecture 승인.** 원본 위치, ID 연결, 승인 역할과 Gate 규칙을 먼저 정한다.
3. **상위 사업·Product 방향을 한 묶음으로 정렬.** Vision의 유지 원칙, 사업 로드맵, 제품 개요, 수익화, KPI를 맞춘다. 상세 수치의 원본을 명시한다.
4. **Validation 허브·레지스트리·결정 로그 연결.** 기존 가설을 추출하되 Evidence를 만들어 넣지 않는다. 사용자 조사·경쟁 서비스·협력 전략·법률/운영과 연결한다.
5. **Home·진행률 갱신.** 준비된 원본을 링크하고 현재 단계와 다음 Gate를 표시한다. 문서 완료 이력을 없애지 않는다.
6. **Release Strategy의 과정/Gate를 정렬.** 기존 04~06·09~10·12장을 중심으로 개발 전 검증과 Cold Start 평가 연결. 이 단계에서는 실제 R1 기능을 확정하지 않는다.
7. **8~12주 검증 실행 후 Product Decision.** Segment/문제·해결 접근법·R1 기능·미해결 위험을 결정한다. 이는 문서 재설계 승인과 별개인 후속 업무다.
8. **승인 R1을 Scenario→Requirement→Feature에 반영.** 보류 기능은 원문/ID를 보존하고 향후 기능에 참조한다. Release Matrix와 같은 변경 묶음으로 검토한다.
9. **IA→Flow→UX 적용표→Screen→Prototype 정렬.** 실제 공개 경로와 핵심 과업·오류·접근성을 맞춘다. 전체 Architecture를 삭제하지 않는다.
10. **Backend와 Frontend 계약 정렬.** 활성 Use Case·API·데이터와 Route·상태·폼·검색·계측을 함께 검토한다. 변경되는 기술 판단은 그 시점에 ADR로 남긴다.
11. **추적표·테스트·운영·출시 조건 최종 점검.** UI/Route/API/권한/접근성/운영/측정의 누락을 확인하고 개발·출시 기준을 승인한다.

Product Decision은 해당 범위 결정 시점에, 기술 ADR는 기술 변경 시점에 기록한다. 모든 수정이 끝난 뒤 사후적으로 근거를 만들어 붙이지 않는다. 승인되지 않은 하위 변경이 현행 계약과 섞이면 `Proposed`로 남기고 Current Baseline을 가리킨다.

## 13. Decision Required

이미 지정한 장기 Vision·청각장애 진입·Notion 미수정·수익 모델 미확정은 다시 결정할 항목이 아니다. 실행 전에 필요한 추가 결정은 다음 네 가지다.

| 결정 | 추천 기본안 | 왜 필요한가 |
|---|---|---|
| Validation에 쓸 시간·예산·주당 운영 가능 시간 | 10주 기본, 최대 12주. 참가 보상·자막/통역·모집·운영 시간을 포함한 상한 설정 | 모집 규모와 Concierge 가능 범위·중단 시점 결정 |
| Gate의 최종 판단자와 검토 방식 | 프로젝트 책임자 최종 결정. 조사 관찰·반증 검토를 별도 시간으로 나누고 당사자 피드백 반영 | 제작자의 확신과 사용자 근거 구별 |
| 문서 컨테이너와 연구자료 권한 | 허브 1+DB 2, 기존 의사결정 페이지 재사용. 원자료 제한 접근 | 관리비용·개인정보 노출 최소화 |
| R1 승인 전 일정 운용 | High-Fi 전면 확장·도메인 전체 구현 약속은 보류하고 검증에 필요한 Prototype만 진행 | 개발 전 검증이 형식적 단계가 되지 않게 함 |

Beachhead·구체 기능·유료 모델은 지금 선택을 요구하지 않는다. 검증 결과를 본 뒤 결정한다.

## 14. 최종 추천안

**IYUM에는 전면 재설계보다 ‘기존 설계의 보존 + 최초 MVP 결정 권한의 Evidence 연결’이 적절하다.**

실제로 적용할 것을 추천하는 변경은 다음과 같다.

1. 8~12주 Product Validation을 Product의 공식 단계로 추가한다. 근거·반증·결정·재검토 조건을 남긴다.
2. 1년 차 목표를 청각장애 내부의 핵심 문제와 초기 Segment, 경험+공식 정보 연결의 실제 가치 검증으로 명확히 한다.
3. 기존 문서/ID/FE·BE 결정을 보존하고 Release 1 포함은 별도의 승인 Matrix로 관리한다. 지금은 기능 삭제나 Segment 확정을 하지 않는다.
4. 이미 있는 Cold Start·Seed·운영 원칙을 활용하고, 실제 사용자 간 답변·문제 해결·재사용·운영자 의존을 Beta 확대 조건에 연결한다.
5. KPI에서 응답과 해결을 구분하고 Validation/Early Product 계층을 추가한다. 기존 Growth 목표는 연간 목표로 보존한다.
6. 수익화는 1년 차 탐색, 2년 차 작은 유료 실험, 3년 차 확대 검증, 4년 차 본격 확장으로 정렬한다. 모델·가격은 가설이다.
7. 관심·상황 선택의 최소 수집, 기본 접근성, 출처·기준일·정보 성격을 실험과 출시의 기본 조건으로 유지한다.
8. 새 문서 원본은 최소화하고 사업 로드맵·KPI·릴리즈 전략·기존 추적표를 재사용한다. 실제 변경 전 Backend 미확인 구간을 재검토한다.

이번 제안의 승인 대상은 **위 문서 재설계 방향과 운영 구조**다. 승인하더라도 특정 Segment의 검증 완료, R1의 구현 범위 확정, 개발 착수 또는 서비스 출시가 자동 승인되는 것은 아니다. 해당 결정은 정해진 Evidence와 Gate를 통해 별도로 구체화한다.

**현재까지 Notion 페이지·데이터베이스·댓글·속성은 변경하지 않았다.**
