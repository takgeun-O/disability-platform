## 1. Phase A.1 실행 요약

Phase A 구조 위에 Search-driven Acquisition / Organic Discovery, Problem-centered Knowledge / Problem Page, Seed Content, 청각장애 아동 부모·보호자 Cohort, 콘텐츠별 검색 노출 검토를 가설·검증 항목으로 반영했다.

## 3. DB / Template 변경

| 대상 | 실제 변경 | 보존 |
|---|---|---|
| 가설 레지스트리 | Hypothesis Type 옵션 1개 추가 | 속성 14개, 기존 10개 옵션·ID·색, 나머지 스키마·Relation |
| 연구 · 실험 기록 | 스키마 변경 없음 | 속성 20개와 가설 Relation |
| Research / Interview Template | Product Validation 8절에 Search Behavior·Organic Discovery 실험 준비 양식 추가 | 기존 관찰·발언·해석·반례·개입·보상 필드 사용 |
| Product Decision Log | 변경 없음 | 기존 위치·본문·상태 축 |

Template은 **허브 본문의 복사용 양식**이며 Notion DB 네이티브 템플릿을 새로 생성한 것은 아니다. 실제 연구 기록의 본문으로 복사하여 사용한다. Search Behavior Observed·Primary Discovery Channel 등의 속성은 분석 필요성이 아직 없어 추가하지 않았다.

질문에는 최근 실제 사건·첫 행동·검색 여부·엔진·실제 Query·검색어 수정·클릭·채널 이동·도움·부족·신뢰·최종 해결·실제 다음 행동을 포함했다. Query는 사용자 언어를 보존하되 개인 식별 정보는 비식별화한다. 기억하지 못하면 미확인으로 기록하고 가상 검색어로 채우지 않는다. 회상과 직접 관찰을 구분한다.

최종 조회에서 가설 DB와 연구 DB 모두 0행이며, Product Decision Log에도 실제 결정은 없다.

## 4. Search-driven Acquisition Alignment

가설 흐름은 다음과 같다.

Problem → Search → Knowledge → Resolution / Next Action → Contribution → Experience Data → Knowledge Improvement → Organic Discovery / Repeat-use.

- 허브 14절: 전체 Loop와 각 단계의 독립 가설.
- 허브 8절: 실제 검색 행동 조사·Organic Discovery 실험 준비.
- 제품 개요: 기존 서비스의 완전 이주를 요구하지 않는 보완적 Distribution Hypothesis.
- KPI: 노출·클릭·CTR과 유용성·해결·기여·재사용을 별도로 측정하는 후보 Funnel.
- 경쟁 서비스: 실제 Current Alternative와 계속 사용하는 장점까지 조사.

실제 경로는 분기할 수 있으며 가입을 거치지 않는 해결도 가능하다. 검색 유입 증가가 해결·가입·기여·Community 자립을 자동 의미하지 않는다. 카페·메신저 재공유, 직접 유입, 운영자 모집은 Organic Search와 구분한다. 검색 순위·검색량·유입 성공·SEO 목표 수치는 생성하지 않았다.

## 5. Parent / Caregiver Alignment

청각장애 아동 부모·보호자를 청각장애 Domain 내부의 별도 Validation Cohort로 명시했다. 기존 당사자 중심 및 Primary/Secondary 분류는 유지한다. 부모를 Primary Segment로 확정하거나 발달장애 부모 시장으로 Pivot하지 않았다.

허브 6절에 반복 탐색·현재 대안의 간극, 공식 정보+부모 경험의 비교 가치, 검색엔진 발견 경로에 관한 예시 가설을 넣었다. 진단 후 탐색·기기 적응/비교·교육/학교 지원·교사와 소통·지원제도 등의 주제는 Problem / Content 후보이며 실제 사용자 발언·의료 조언·Content Roadmap이 아니다. 모든 예시는 DB 행·ID 없이 문서 양식으로만 존재한다.

## 6. Seed Content Strategy

운영 정책 3장을 원본으로 세 공급 경로를 구분했다.

- Editorial / Official Information: 운영자 작성과 공식·검증 가능한 출처, 기준일·검토일·성격·대상/조건·공식 경로 표시.
- Interview-based Experience: 실제 사례 중 별도의 Public Content 동의를 받은 내용만 비식별 검토 후 활용.
- UGC: 사용자가 직접 작성한 질문·답변·후기·경험·팁·해결 결과.

Research Participation Consent는 Public Content Consent와 다르다. 운영자 콘텐츠는 IYUM Editorial, Founder의 실제 경험은 Founder Experience 등으로 출처를 표시한다. 허구 계정·후기·댓글·질문·답변·AI 생성 경험을 실제 사용자 활동처럼 표시하지 않는다. 공급 비율 KPI·정책 글 대량 생산·초기 콘텐츠 우선순위는 확정하지 않았다.

## 7. Indexability / Privacy

운영 정책의 개념적 분류를 법률 검토와 허브에서 참조한다.

| 콘텐츠 | Phase A.1 원칙 |
|---|---|
| Public Editorial / Knowledge | Index 가능 후보 |
| Public Problem / Knowledge Page | 가설·공개 기준 승인 후 Index 가능 후보 |
| Public Community | 기대·동의·콘텐츠 성격에 따라 검토 |
| Member-only | 검색 노출 대상 아님 |
| Sensitive Personal Experience | 기본적으로 매우 신중한 검토, 자동 노출하지 않음 |

아동 이름을 제거하고 학교·학급·구체 지역 등 식별 가능한 정보를 최소화한다. 연구/공개 목적을 분리하고 불필요한 의료정보를 수집하지 않는다. 공식·전문 출처와 개인 경험을 구분하며 특정 치료·기기 선택을 개별 의료 판단처럼 권고하지 않는다.

이는 문서 원칙의 보완이다. 현재 사이트 공개 범위·로그인·Index/noindex·권한·동의 UI를 변경하지 않았으며, 최신 법률 자문이나 실제 권한 설정 완료를 의미하지 않는다.

## 8. Phase B Deferred

실제 Evidence·Product Decision·Release 승인 이후 다음을 검토한다.

- Problem Page의 실제 필요성과 기존 Domain 정보를 연결할 표현 구조.
- Public Page·비로그인 열람 범위, Stable/Shareable URL, Index/noindex, robots, Sitemap, Canonical.
- Page Title·Meta Description·Semantic Heading·Crawlable HTML·Internal Linking·Structured Data.
- Last Updated·Source/Provenance·Crawlability·Duplicate Content 관리.
- 승인된 요구에 따른 Scenario·Requirement·Feature·IA·Flow·Screen·Public Route·Search·Backend·Frontend 정렬.
- 실제 필요성이 승인된 뒤 SSR/SSG/ISR·Framework·Search SDK·Analytics·CMS·CDN 판단.

현재 URL·Route·Screen ID·Problem Entity·DB Schema·Search Index/API·Frontend Component는 생성하지 않았다. 기존 Required / Optional / Deferred, Authentication, AI Architecture, ADR, 실제 구현 추적 상태도 유지했다.

## 10. Verification Result

수정 전 지정된 18개 문서/DB를 조회했고, 실제 수정 직전·직후 및 마무리 단계에서 다시 조회했다. 수정한 10개 페이지의 최종 본문은 의도한 치환 결과와 일치한다(공백·Notion의 native mention 표현 정규화 후 비교). 조회 결과의 truncated/unknown block은 모두 없었다.

릴리즈 전략 전체 본문, 사업 로드맵 본문, Product Decision Log 본문, 기존 KPI 1장 이후, 연구 DB 스키마, 허브 하위 문서 구조가 동일함을 확인했다. 가설 DB의 기존 옵션 ID·색·명칭과 다른 속성도 동일하다. 경쟁 서비스 1장의 기존 접기 형식·중첩은 최종 복원 후 정확히 동일하다.

| 번호 | 검사 | 확인 근거 |
|---|---|---|
| 1 | Phase A 구조 보존 | 허브 하위 DB·페이지 링크 동일; 새 Notion 페이지 없음 |
